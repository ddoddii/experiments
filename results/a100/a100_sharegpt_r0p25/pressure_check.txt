========================================================================
 PREFILL KV POOL 압박 점검 -- victim cache 가 잡을 것이 있었는가
========================================================================
  arm                      capacity  peak used  peak util     hit
  ----------------------------------------------------------------
  hicache                    105000       7500       7.1%  0.940   <-- 차지 않았다
  park_gpu                   105000       5343       5.1%  0.931   <-- 차지 않았다
  recompute                  105000       5569       5.3%  0.000   <-- 차지 않았다

  경고: 3개 arm 에서 prefill 풀이 60% 미만으로만 찼다.

  풀에 여유가 있으면 밀려나는 KV 가 없고, hicache 의 L2/L3 도 park 풀도
  받을 것이 없다. 남는 것은 비용뿐이므로 이 상태의 TTFT 비교는
  'victim cache 가 효과 없다' 가 아니라 '측정할 조건이 아니었다' 를 뜻한다.

  풀을 워크로드에 맞게 줄여서 다시 돌려라 (모든 arm 에 똑같이 적용해야 한다):
    ./scripts/slurm/submit.sh MODE=full PREFILL_MAX_TOTAL_TOKENS=3000 \
        MOONCAKE_LD_FIX=system MC_FORCE_TCP=1

  (hicache 의 peak used 가 7500 로 가장 크므로, 그 절반이면 약 2배
   oversubscribe 된다. 카드가 A6000 48GB 에서 A100 80GB 로 커지는 동안
   워크로드가 그대로여서 압박이 사라진 것이 원인이다.)

  ─── 동시성을 올려서 압박을 만들려면 ───────────────────────────
  이 run 의 동시 세션당 몫: 7500 / C=32 = 약 234 tokens
  (BFCL 은 tool 정의가 매 턴 재전송되는데 item 마다 tool 조합이 달라서
   세션 간 공유가 약하다. 그래서 C 에 거의 비례해 점유가 오른다.)

       C        예상 점유    capacity 대비
      32         7500             7%
      64        15000            14%
      96        22500            21%
     128        30000            29%

  풀을 100% 채우려면 C≈448, 2배 oversubscribe 하려면 C≈896 이 필요하다.
  BFCL 은 item 이 200개뿐이라 C 가 그쯤 되면 데이터셋 대부분이 동시에 떠서
  TTFT 가 사실상 큐 대기 시간이 된다 -- prefill 효과를 재려는 지표가
  다른 것을 재게 된다. 그래서 풀을 줄이는 쪽이 변수를 하나만 움직인다.
